## 一、为什么引入 Rerank 模型代替 RRF？

### 1.1 传统 RRF (倒数秩融合) 的局限性
在传统双路召回（BM25 词频检索 + Dense 向量检索）中，工业界常使用 RRF（Reciprocal Rank Fusion）进行粗排融合：
$$RRF\_Score(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
虽然 RRF 简单且无需训练，但其存在三大致命工程缺陷：
1. **纯位置排序，抹平绝对相关度**：只要候选商品在 BM25 或向量列表中排在首位，无论其与用户 Query 的真实语义相似度是 0.99 还是 0.15，RRF 给予的增益完全相同；
2. **缺乏全交互交叉注意力 (Cross-Attention)**：双路召回采用双塔架构（Bi-Encoder），文档和 Query 的表征在进入检索池前是完全解耦独立的，无法捕捉 Query 词与商品参数之间的细粒度交叉匹配；
3. **电商多维属性融合失真**：电商导购高度依赖核心参数规格（如功率 65W/100W、接口数 3口/4口、屏幕尺寸 17寸、轴体红轴/青轴）以及品牌属性。RRF 无法依据电商导购场景赋予关键规格更高的特征交互权重。

### 1.2 工业级 Cross-Encoder 精排重排器架构
本项目实现 `EcommerceCrossEncoderReranker`（位于 `app/services/multimodal_rag.py`），支持 `mode="hybrid_rerank"`，作为业界最优推荐链路：
- **深度全交互交叉打分 (Cross-Attention Scoring)**：对 Query 与商品标题（35%）、规格参数（30%）、核心卖点（20%）及品牌类目（15%）进行词元级深度交叉感知；
- **连续概率分布输出**：输出 0.0 ~ 1.0 的连续相关度分值（精准到浮点后 6 位），保留真实置信度；
- **电商多维硬软规格动态加权**：与 `ConstraintExtractor` 提取的硬规格与软偏好紧密联动，避免属性漂移；
- **消融实验实测收益**：在多模态精准搜索基准中，Cross-Encoder 精排在保持 0.0% 硬约束违规率的同时，输出细粒度连续打分，比纯 RRF 更具工业解释性与可信度。

## 二、四层根因归因闭环：盲调 Prompt 为什么越调越差？

### 2.1 工业痛点剖析
很多团队在优化 Agent 效果时，只要评测失败或线上用户不满意，第一反应就是去修改 System Prompt。
**不做归因就盲目调 Prompt，为什么可能越调越差？**
1. **真实问题在数据层（DATA_LAYER）**：
   - *案例*：用户询问“有没有防蓝光又带气囊的17寸电脑包”，自营库里根本没有上架这款商品。
   - *盲调后果*：若盲调 Prompt 让模型“尽可能满足用户需求”，大模型就会开始无中生有、编造价格和虚假功能，直接击穿 L3 自然语言逆向闭包红线；
2. **真实问题在智能体核心逻辑（AGENT_CORE）**：
   - *案例*：用户在多轮对话第 2 轮说“放宽预算到 35 块”，由于未维护决策账本，丢失了上一轮锁定的“电脑包”类目，导致 RAG 搜出键盘或冲锋衣。
   - *盲调后果*：在 Prompt 里写“请注意不要遗忘品类”，但由于上下文窗口膨胀或注意力串扰，大模型依然会偶发漂移，且大幅浪费 Input Tokens；
3. **真实问题在评测标定层（RUBRIC_LAYER）**：
   - *案例*：评测集里的 expected_intent 标定错误，或用例本身存在二义性（例如用户问“有现货吗什么时候发货”，标注期望只查订单而非商品答疑）。
   - *盲调后果*：为迎合错误的用例标注去改动路由逻辑，会破坏正常的线上真实业务交互。

### 2.2 四层归因系统的自动化实现链路
在 `app/core/assertion_engine.py` 中实现了 `AttributionClassifier` 与 `CNTFunnelEvaluator`：

```
[用户请求输入 / 评测用例]
           │
           ▼
┌──────────────────────────────────────────────┐
│       CNT 六层短路熔断引擎 (Fail-Fast)        │
│  L1_CTX -> L2_OOSR -> L3_OOC -> L4_TCC       │
│               -> L5_CNT -> L6_RED            │
└──────────────────────┬───────────────────────┘
                       │ (若某一层熔断)
```

## 三、分级决策账本 (Hierarchical Context & Decision Ledger Harness)

### 3.1 核心机制
位于 `app/core/context_harness.py`：
1. **决策工作账本 (Decision Ledger State)**：
   - 提取并压缩为结构化字段：`locked_sub_category`、`budget_min/max`、`specs_constraints`、`evaluated_skus`（保留最近 3 款已推荐商品元数据）、`focused_sku_id`、`decision_stage`；
   - 渲染为紧凑纯文本，严控在 **60~100 Tokens**，彻底消除长上下文下的注意力串扰与前置商品遗忘；
2. **分级活跃窗口 (Active Dialogue Window)**：
   - 活跃区：保留最近 2~3 轮的高保真多轮问答；
   - 归档区：将超过活跃窗口的更早轮次折叠为 1~2 句核心要点回顾；
   - 降低 Token 消耗 60%+，使得对话在 20+ 轮交互中依然保持注意力聚焦与确定性。
