# 功能演进规划与 Sunset（优雅日落）规范

> 本文档落地天猫 MDI 研发协同实践中的 **启发 4（生命周期治理与 Sunset 日落机制）**，以及 **启发 1（软硬双锁）** 与 **启发 2（上下文缝补）** 的工程分界规范。

---

## 一、启发 1 与启发 2 的架构应用区分

### 1. 启发 1：软硬双锁（Harness Engineering）—— 应用于「C 端惠购对话与 Generative UI 渲染层」
- **核心目标**：消费者端的不确定性最高，必须“在交互体验上做加法（Generative UI），在事实与排版稳定性上做物理硬约束”。
- **软锁（行为层）**：
  - 通过 System Prompt 约束导购语气简洁自然，不输出长篇累牍的参数堆砌与解释性小字。
- **硬锁（协议层，物理不可绕过）**：
  1. **文本净室硬锁**：后端 `SlidingWindowStreamFilter` + 前端 `streamSanitizer` 双重拦截 `<br>`、HTML 标签、LaTeX 数学符号（`$...$`、`\rightarrow` 等）与伪造优惠券话术。
  2. **Generative UI 数据硬锁**：所有 `product_card`（商品价格/立减）、`comparison_card`（双路径松弛差价）、`order_card`（168h 退货时效 / 360h 价保退差金额）、`wishlist_card`（缺货品类心愿单登记）的数值与状态 100% 由后端确定性引擎生成并经 `event: ui_cards` 下发，大模型在协议层无权篡改任何金额或库存字段。

### 2. 启发 2：上下文缝补（Context Stitching）—— 应用于「B 端 OA 管理后台与诊断层」
- **核心目标**：当商品规格注册表（`spec_registry.json`）、60 款全平台商品（`ecommerce_catalog_60skus.json`）、缺货品类心愿单钩子（`wishlist_hooks` 表）及反馈日志外置到 DB/配置文件后，消除管理员与研发排障时的“推理链断裂”。
- **落地方案**：
  - 后端暴露只读缝补接口 `GET /api/v1/admin/context-manifest`，实时聚合当前生效的：**静态前缀缓存 Hash（`4729a6f0...`）+ 全平台 3 大领域 17 个子类目 SKU 覆盖矩阵 + 5 组冲突松弛规则对 + C 端未覆盖品类心愿单高频词**，并在 OA 管理后台直观呈现。

## 二、Sunset（优雅日落）机制与当前已日落模块

当旧功能或过渡期方案被新架构替代时，**严禁直接粗暴 `git rm` 导致历史回归测试断裂**，必须走三步日落状态机：
1. **`FREEZE`（凝固期）**：标注日落声明，停止新增功能与样式修改，仅保留向后兼容路由；
2. **`MIGRATE`（流量切换期）**：主入口与导航全面切向新模块，监控旧入口调用量；
3. **`ARCHIVE`（清场归档期）**：待新版本全量稳定后归档移除。

### 日落档案 002：C 端多店铺切换栏（Multi-Store Tenant Switcher in H5）

> ⚠️ **日落声明（过渡态 · 三店铺前端切换器）**
> - **当前状态**：`SUPERSEDED`（已被全平台统一导购 + 缺货心愿单钩子替代）
> - **演进原因**：「惠购」定位为全平台统一 AI 购物助手，覆盖平台全部在售商品，无需让消费者手动切换“3C店/服饰店”。
> - **新方案（全平台检索 + 缺货心愿单钩子 `wishlist_card`）**：
>   - 默认在全平台 60 款 SKU 中精准导购；
>   - 当用户咨询平台暂未上架的品类（如空气炸锅、显卡、猫粮、跑鞋等）时，自动触发 `wishlist_card` 缺货反馈钩子（“暂无当前商品，点击登记心愿单，我们会尽快上架”），并将用户需求实时汇聚至 OA 管理后台的「缺货心愿单」模块供采买团队决策。
